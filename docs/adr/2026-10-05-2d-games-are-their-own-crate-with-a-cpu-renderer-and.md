# 2026-10-05. 2D games are their own crate with a CPU renderer and shared semantics

> **Superseded 2026-10-07:** the browser target was removed (ADR 2026-10-07-native-executables-only-the-browser-target-is-removed), so the `cdylib` WebAssembly player and "one definition runs in the browser" are gone. What still stands, and is how `crates/red2d` works today:
> the crate boundary, the declarative JSON, the deterministic simulation, the CPU rasteriser and the shared sound/validation files; `red2d` is an `rlib` that the CLI and the native player (`play2d`, `re2d`) link. Kept as history.

Status: superseded by 2026-10-07-native-executables-only-the-browser-target-is-removed
Summary: 2D games live in the red2d crate (declarative JSON, deterministic simulation, CPU rasteriser, shared sound/validation files), so one definition runs natively and in WebAssembly without a rewrite of the 3D engine.

## Context
The goal was a working path from "an AI makes a small game" to a playable browser URL, on top of an engine whose renderer is wgpu, whose simulation is the authoritative 3D `MatchSim`, and whose library (rapier, quinn, tokio, wgpu, winit) does not build for `wasm32-unknown-unknown`. Three options were weighed: (1) compile the whole engine to WebAssembly and render with WebGPU; (2) a 2D mode inside the scene format and the 3D renderer; (3) a separate small crate. (1) needs a browser GPU stack, a port of the networking and physics dependencies and a CI browser with a GPU; (2) forces 3D concepts (cameras, lights, meshes) into every 2D file and 2D tooling into the 3D renderer.

## Decision
2D games are their own workspace crate, `crates/red2d`, with two crate types: an `rlib` the CLI links (headless play, `verify`, `frame`, packaging) and a `cdylib` that is the WebAssembly player. A game is one JSON file, `NAME.game2d.json`, parsed by the same strict field tables as 3D (`src/fields.rs`, extracted from `strict.rs`, with `src/suggest.rs`). The simulation is a fixed 60 Hz step with a seeded RNG, IEEE basic operations and `libm` trigonometry, so it is bit-identical natively and in the browser (checked: `web verify` makes the browser reproduce every native scenario hash). Rendering is a **CPU rasteriser** to an RGBA buffer, shown on a canvas: no GPU, no WebGPU, and a native screenshot is the player's pixels. Sound reuses the 3D engine's voice and score descriptions, renderer and analysis by `#[path]` includes of dependency-free files (`rules_expr`, `synth`, `dsp`, `audio_analysis`, `voice_spec`, `audio_fx`, `score`), so there is one expression language and one audio model. The existing verbs (`validate`, `verify`, `sim`, `frame`) route by file name; the 3D crate, renderer and server are unchanged.

## Consequences
Easier: a 2D game is small, strict and cheap to author (one file, one reference page, `describe 2d`), verified without a window or a browser, and the browser build is a thin shell. Harder: two presentations to keep honest about shared meaning; `red2d` sees changes in the included engine files (`affected` plans its tests when one changes); a CPU rasteriser is the wrong tool for large or effects-heavy 2D (the declared limit is a 1280-px virtual screen and sprites up to 64 px). To undo: delete `crates/red2d`, `src/tools/game2d.rs`, `webpkg.rs`, `webverify.rs`, `src/cli/web.rs`; the extracted `fields.rs`/`suggest.rs` stand on their own. A native window for 2D games is prepared (the app layer's shell could show the CPU frame) and deliberately not built.
