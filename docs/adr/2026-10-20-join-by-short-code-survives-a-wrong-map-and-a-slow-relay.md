# 2026-10-20. Join by short code survives a wrong map and a slow relay
Status: accepted
Summary: A JOIN runs on a worker thread, asks the relay again for every map it tries, repeats Resolve and Claim inside their time budget, and says which cause stopped it, all on the unchanged wire (protocol 17, the deployed relay, release 4 clients).

## Context
Two players who live in different states never managed to play Killchain together. A connectivity investigation (2026-10-20) found the network fine (a runner on four other networks completed a relay `Resolve` and a QUIC handshake against the home server) and a chain of client defects, each enough to end a join:

- JOIN resolved a short code **once** and reused that claim for every installed map. The host plays one map and a joiner must hold the same file, so the client tries the maps in turn; but a relay `Claim` is single-use and bound to the socket that sent it, so the second attempt never paired and the join ended "no answer from the server within 6 s" instead of connecting. The README said the game tried each map.
- Resolving and connecting ran on the thread that draws the window: up to 5 s plus 6 s per map with "CONNECTING..." set and never painted ("Not responding", then the player quits). HOST did the same for the relay `Register` (50 s when the relay is down) and for the router's UPnP discovery (3 s and more).
- `Resolve` and `Claim` were one datagram each, and every failure was worded "check your internet connection".
- The lobby listed only the first code, upper-cased a direct code (`SHA256:` then parses as a join key), cut it with an ellipsis in a small window and had no COPY button.
- A host never learned that the relay had restarted and given it a new code; a relay that was down at the start left the game without an online code for good.
- The three releases (protocols 15, 16, 17) are mutually incompatible and nothing in the UI said which one a player had.

## Decision
No protocol change: everything here interoperates with the relay and server already deployed and with release 4 clients (`relay.rs` has golden bytes for every control message, `tests/net_join_flow.rs` speaks them by hand).

1. **JOIN is a task, not a call.** `net::join_task::JoinTask` runs the whole join on a thread; the window asks it once a frame for a status line and an outcome, and can cancel. HOST registers with the relay and asks the router on threads of their own (`LocalHost` states, polled by the lobby).
2. **Every map is a fresh attempt.** The alternatives were to learn the host's map first (impossible: a `Reject` and a `Challenge` carry no map, and adding one is a wire change) or to keep one claim (it cannot work). So each attempt resolves again and connects from a new socket; the map that worked with a code last time is tried first, which makes the common case one attempt. A host that stays silent is asked once more with a fresh claim before the join gives up; a host that matches no map is told so.
3. **Repeating `Resolve` and `Claim` is safe, so they are repeated.** The relay mints a new token for every `Resolve` of a live code and keeps each for 15 s (a repeat is one unused token, bounded by its caps), so `Resolve` goes out four times inside its budget and the first answer wins. A token is consumed by the first `Claim` that names it; a second copy finds nothing and is ignored, and once the address is paired the relay forwards whatever else it sends as opaque bytes, which the game server drops (the claim's first byte, 6, has the QUIC fixed bit clear). So the `Claim` is repeated from the same socket while the QUIC handshake runs and stops when it ends or the client closes. The alternative, repeating only until the first reply, needs a hook into quinn's socket for a gain of a few datagrams on a good link.
4. **Failures are worded by cause.** The name does not resolve; the relay's machine says nothing listens (the join uses a connected UDP socket so the bounce is visible); the relay does not answer (down, or the network drops UDP); the code is not live; the host did not answer; the host refused (key, full, map, protocol). Each says what to do next. A version refusal says what this copy is (`release 4, protocol 17`, from `play.cfg` next to the executable, which the release tool writes) and that both players need the newest release: the wire carries only the reason, so it cannot say which side is behind or the host's number.
5. **Codes are text a person handles.** The lobby lists every code with what it is for, in full, wrapped, in its own case, with a COPY button for each; the card shrinks only when it must. `JoinCode::parse` ignores a label, white space, a trailing newline, `SHA256:`'s case and the hex's case, and finds the code in a pasted file (`extract_code`).
6. **No key in the repository.** An "OFFICIAL SERVER" button would have to contain the server's join key, which would be public. JOIN instead remembers the last three games that worked in the player's own `stats.json` (key included, local only) and offers them as one-click REJOIN buttons labelled with the address or the six characters, never the key; the owner sends the code once.
7. **A host's code follows the relay.** The keepalive's `Registered` answer (from the relay's address only) updates the code the lobby shows, with a line saying it changed; a relay that was down at the start is asked again every 20 s.

## Consequences
- A joiner whose selected map is not the host's gets in; a joiner on a network that loses a datagram usually does too; one on a network that drops UDP is told so and what to try (a phone hotspot, the long code). There is still no TCP fallback.
- Each rejected map leaves a pairing at the relay for up to ten minutes (there is no "release" message): three attempts cost two stale pairings of the relay's 128, which is why the map that worked is tried first.
- `relay_server.rs` fell under the long-file limit by moving its tests to `relay_server/tests.rs` (it left `LONG_FILES`).
- Proof: unit tests beside each piece, and `tests/net_join_flow.rs`: a wrong first map, every cause's words, a lost `Resolve`, a lost `Claim`, repeated claims on a slow link, a join that never blocks the caller, and the bytes of a released client against the current relay.
